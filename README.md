# llmlab

> What the money and failure behaviour of an LLM gateway actually is, **measured**.
> Fault injection into a gateway, one command, no network, milliseconds.

`llmgateway` claims a cap you cannot bypass, failover that tells provider errors from client
errors, and metering that never loses a response. Claims become credible when somebody else can
reproduce the numbers. This repo drives the **real gateway code** — taken as a dependency, not
copied — with a fake provider that can be told to fail in specific ways, and publishes what
happened.

```bash
make lab     # runs every scenario, writes reports/latest.{md,json}
make ci      # fmt + clippy -D warnings + the assertions
```

No API keys, no network, no ports: a full run takes milliseconds, so it can be the thing CI does
on every commit.

## What it measures, and what came out

Every number is from `reports/latest.md`, regenerated by `make lab`. The `cargo test` suite
asserts the same invariants, so a regression fails the build instead of quietly changing the
report.

| Scenario | What was measured | Why it matters |
|---|---|---|
| Cap holds before the spend | 10 requests against a 7 µUSD cap → 5 served, 5 rejected with `429`, and the provider was called **exactly 5 times** | the rejected requests never cost anything: that is the difference between a cap and a report |
| Reservation is pessimistic | estimate 3 µUSD per request, real cost 1 µUSD, surplus 2 µUSD | the cap rejects earlier than pure spending would — the measured price of checking before the call |
| Provider error | `503` from the first provider → client gets `200`, served by the second; calls `provider-a: 1, provider-b: 1` | failover that the client never notices |
| Client error | `400` from the first provider → client gets `400`, calls `provider-a: 1, provider-b: 0` | an error of the client is not retried on someone else's account |
| Request that may already have been executed | provider dies after receiving → client gets `502`, second provider calls `0`, spend `0` | retrying could charge twice, so it does not retry |
| Money vs metrics | 100 requests → spent **100 µUSD exactly**, while the `served` counter reports **0** at 1-in-1000 sampling | invoice on the money, dashboard on the counter, never the other way round |
| Streaming | forwarded as a stream, spend `0` | declared, not surprising: usage of a stream arrives in its last chunk, which the gateway never buffers |

## How it works

```
FakeProvider (Upstream)  ──►  Router (failover)  ──►  Gateway::handle  ──►  Budget + Meter
   behaviours,                    real code              in-process            real code
   call counters
```

Three properties, because a measurement you cannot trust is worse than no measurement:

- **the real code, not a model of it**: `llmgateway` comes in as a Cargo dependency and
  `Cargo.lock` pins the exact revision that was measured;
- **no network**: the provider is a trait implementation in this process. Nothing here can be
  slow, unavailable, or expensive, so the numbers are about the gateway and nothing else;
- **invariants are assertions**: `cargo test` fails if a rejected request starts reaching a
  provider, if the cap stops holding, if a reservation is left pending, or if money stops being
  exact.

## Scope, declared

Not here yet, and not claimed:

- **the HTTP adapter.** `llmgateway` is a library today: no binary, no `axum`/`reqwest` adapter,
  so this lab drives `Gateway::handle` in-process. Same code path for auth, cap, routing and
  metering; different thing from a client on the wire.
- **the agent side.** An `agentloop` run driving this gateway over HTTP, with its own budget and
  its replay, is the natural next scenario. It needs the HTTP adapter first, and it makes the
  lab stop being milliseconds — which is why it will be a separate target, not the default one.
- **latency.** Only money and failure semantics are measured. A latency distribution would need a
  real transport, and this lab deliberately has none.

## What I would do differently

- The fake provider lives here while `llmgateway` has its own for unit tests. Two fakes, one
  concept: it should be one crate both can depend on, and today it is not.
- `reports/latest.md` carries a timestamp, so every run dirties the working tree. A `--check`
  mode that compares numbers against a committed baseline, instead of rewriting them, would be
  the honest version of "the numbers changed".
- The scenarios are hand-written. A table-driven version would make adding the seventh scenario a
  data change instead of a code change — worth doing the third time it hurts, not before.

## Development

```bash
git clone git@github.com:paoValle/llmlab.git
cd llmlab
make lab && make ci
```

Depends on [`llmgateway`](https://github.com/paoValle/llmgateway) at build time, and on nothing
else: no provider, no key, no container.
